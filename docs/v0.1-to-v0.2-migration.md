# AgentCanvas v0.1 to v0.2 migration

The current CLI continues these schema-4 milestones through the verified offline 4→5 migration; see [Upgrading](upgrading.md#030-alpha6-permanent-canvas-deletion-physical-schema-5).

Status: operator guide for the implemented offline legacy-import path. The
current target is physical schema 5 / document schema 2; new operators must
still migrate each v0.1 database independently.

## Before you begin

1. Build the plugin catalog.
2. Materialize the three defaults.
3. Use `inspect` to identify every importer required by the database, then install the corresponding optional plugins from the catalog.
4. Verify the complete required plugin set.
5. Keep AgentCanvas running only for the first read-only inspection. Stop it before `apply`, `verify` if coordinated with cutover, or `restore`.

The migration loads plugin importers offline and does not run provider readiness probes. It still requires every importer-owning plugin to be present in the selected plugin directory.

## Commands

```bash
npm run migrate -- inspect --database <path> [--json]
npm run migrate -- apply --database <path> [--backup-dir <path>] [--plugins <path>]
npm run migrate -- verify --database <path> [--plugins <path>]
npm run migrate -- restore --database <path> --backup <path>
```

Run these commands from the AgentCanvas checkout. After `npm ci`, the equivalent local-bin form is `npm exec -- agentcanvas migrate <command> ...`; no global executable is required. The binary uses Node 24's native SQLite API through the repository's `tsx` runtime dependency.

## Inspect

`inspect` opens the database read-only. It reports physical/document versions, integrity and foreign-key checks, counts, type mappings, required importers, runtime-only fields, group blockers, duplicate IDs, malformed JSON, unknown types, unexpected fields, intended backup path, and whether apply is allowed.

Migration blocks on:

- any legacy `group` record;
- unknown legacy types or fields;
- missing/malformed element IDs or JSON;
- duplicate IDs within a canvas;
- contradictory document versions;
- SQLite integrity or foreign-key failures;
- missing plugin importer or target validation failure during apply.

## Type mapping

The installed first-party importers map legacy element types to namespaced v0.2 types:

| v0.1 type | v0.2 type |
|---|---|
| `asset` | `agentcanvas.assets2/asset` |
| `markdown` | `agentcanvas.markdown/document` |
| `text` | `agentcanvas.primitives/text` |
| `shape` | `agentcanvas.primitives/shape` |
| `line` | `agentcanvas.primitives/line` |
| `arrow` | `agentcanvas.primitives/arrow` |
| `table` | `agentcanvas.table/table` |
| `bboxOverlay` | `agentcanvas.image-overlays/bbox` |
| `pathOverlay` | `agentcanvas.image-overlays/path` |
| `video` | `agentcanvas.video/video` |
| `glbViewer` | `agentcanvas.glb-viewer/model` |
| `group` | removed migration blocker |

Treat the `inspect` report for the selected database as the authoritative baseline. Archive that report privately and use its counts and preservation fingerprints for post-apply verification; do not substitute counts from another installation.

## Apply semantics

`apply` refuses `:memory:` and requires exclusive SQLite access. It:

1. runs preflight inspection;
2. proves exclusive access;
3. creates a consistent native SQLite backup;
4. writes and verifies `<backup>.manifest.json` with path, length, SHA-256, versions, timestamp, counts, and tool version;
5. begins an exclusive transaction and rejects source changes since backup;
6. runs each pure legacy importer twice and requires deterministic equal output;
7. validates every canonical envelope and active plugin schema;
8. updates current canvases to document version 2;
9. marks historical event bodies document version 1 without rewriting their JSON;
10. clears and recreates the idempotency table at document version 2;
11. adds installation, migration, plugin-migration, and plugin-KV schema;
12. verifies preservation fingerprints, counts, integrity, foreign keys, and target schemas;
13. commits only after transaction-local validation succeeds;
14. reopens and verifies the committed database.

A failure rolls back the open transaction and retains the backup, manifest, and a failure report when possible.

## Verify acceptance

For the selected database, require:

- exact canvas, canonical-element, share-link, and historical-event counts from its archived `inspect` report;
- exact per-type mappings reported during preflight;
- zero current legacy types and zero groups;
- the expected audited count of stripped runtime-only fields;
- the expected invalidation count for v0.1 idempotency responses;
- preserved version-1 event bodies and share links;
- integrity and foreign-key checks passing;
- physical/document version 4/2 metadata and one completed host migration ledger row.

The verifier also requires the target tables, including `plugin_migration_runs`, `plugin_kv`, and the macro storage tables. On an existing v0.2 database, `npm run migrate -- apply ...` creates a verified backup and routes physical 2/2 or 3/2 state through the dedicated physical schema 4 core migration. For physical 3/document 2, that first apply preserves existing canvas, event, and idempotency rows. If installed-plugin forward schema migrations remain pending, run a subsequent offline apply/verify cycle; do not assume one physical-3 apply performs both core and plugin migrations. See [physical schema 4 migration](physical-schema-4-migration.md) for the source-state matrix and preservation-fingerprint checks.

## Restore

`restore` requires the backup sidecar manifest and verifies its recorded source path, length, SHA-256, counts, and supported source-version state. It accepts a v0.1 migration backup and the physical/document 2/2 or 3/2 backups described in [physical schema 4 migration](physical-schema-4-migration.md). It creates a native SQLite staged copy, preserves the current database as a timestamped `failed-v0.2` database, moves WAL/SHM sidecars with it, and atomically renames the verified source database into place.

The target service must be stopped. Restore refuses if staging or failed-database paths already exist.

## Cutover checklist

- If the optional Assets-2 extension is installed, verify its identity, capabilities, and health.
- Build the catalog, materialize defaults, and install every optional plugin importer identified by `inspect`.
- Inspect and archive the JSON report.
- Stop AgentCanvas through the deployment's process or service manager.
- Apply and verify the migration.
- Start AgentCanvas and verify health, identity, plugin catalog, representative reads, shares, resources, snapshots, HTTP MCP, stdio MCP, and browser interactions.
- If an acceptance check fails, stop AgentCanvas and run the manifest-verified restore.
- Retain the v0.1 backup until an explicit retention decision.

## Reference cutover status

The reference deployment completed its cutover on 2026-07-13. It created and verified a native SQLite backup before mutation, reproduced its private preflight counts and preservation fingerprints, passed integrity and foreign-key checks, and completed health, Assets-2 readiness, plugin, HTTP, MCP, snapshot/resource, and production-browser acceptance.

Deployment-specific migration IDs, database counts, backup filenames, hashes, and retention records are intentionally kept in the operator's private change record rather than this public guide.
